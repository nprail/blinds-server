# Using an EBYTE E32 LoRa UART module

blinds-server supports two RF hardware options:

| Driver | Module | Interface | Use case |
|--------|--------|-----------|----------|
| `sx1278` (default) | SX1278 breakout board | SPI | Emulates 433 MHz OOK remotes — ideal for controlling existing AC123-16D-style blind motors with their original remote protocol |
| `e32` | EBYTE E32 (E32-433T20D, E32-433T30D, etc.) | UART (serial) | LoRa transparent mode — ideal for custom setups where both the Pi and the blind controller use E32 modules |

> **Important:** The E32 transmits LoRa-modulated packets, **not** raw OOK
> waveforms.  It **cannot** directly emulate a standard 433 MHz OOK remote.
> Use this driver when your blind controller also has an E32 (or compatible
> LoRa) receiver, or when you are building a fully custom RF link.
> To control AC123-16D-style motors with their original protocol, use the
> default `sx1278` driver.

---

## Hardware requirements

- EBYTE E32-433T20D, E32-433T30D, or any compatible E32 series module
- A second E32 module (or compatible LoRa receiver) at the blind motor end
- Jumper wires (female-to-female for direct GPIO connection)
- 3.3 V or 5 V power supply — check your specific module's datasheet

---

## Wiring

Connect the E32 to the Raspberry Pi's hardware UART and two GPIO control pins:

| E32 Pin | Pi GPIO (BCM)       | Pi Header pin | Function        |
|---------|---------------------|---------------|-----------------|
| VCC     | 3V3 or 5V           | 1/2 or 4      | Power           |
| GND     | GND                 | 6, 9, 14 …    | Ground          |
| TXD     | GPIO 15 (RXD)       | 10            | UART RX → Pi    |
| RXD     | GPIO 14 (TXD)       | 8             | UART TX → E32   |
| M0      | GPIO 17 (E32_M0)    | 11            | Mode control    |
| M1      | GPIO 27 (E32_M1)    | 13            | Mode control    |
| AUX     | GPIO 22 (E32_AUX)   | 15            | Busy/ready pin (optional but recommended) |

> **Tip:** The AUX pin allows the driver to wait until the module has finished
> transmitting before returning.  If you don't wire AUX, the driver falls back
> to a fixed delay; this is usually fine but slightly less reliable.

---

## Enabling the hardware UART on Raspberry Pi

The built-in serial port on Pi 3/4/5 is shared with Bluetooth by default.
Run `sudo raspi-config` and choose:

```
Interface Options → Serial Port
  → Login shell over serial: No
  → Serial port hardware enabled: Yes
```

Then reboot.  Verify the port is available:

```bash
ls -la /dev/ttyS0
# or /dev/ttyAMA0, /dev/ttyUSB0 (if using a USB-to-serial adapter)
```

## Configuration

Set `RF_DRIVER=e32` in your `.env` file (or in Docker via env variables) and
configure the E32-specific variables:

```env
# Switch to the E32 UART LoRa driver
RF_DRIVER=e32

# Serial port (adjust to match your Pi model / adapter)
E32_UART_PORT=/dev/ttyS0
E32_UART_BAUD=9600

# GPIO pins for mode control
E32_M0_PIN=17
E32_M1_PIN=27

# Optional: GPIO pin for AUX (busy/ready detection)
E32_AUX_PIN=22
```

`RF_FREQUENCY_HZ` and `RF_REPEAT_COUNT` still apply — they are passed to the
Python script and control how many times the packet is re-sent.

> **Note:** `RF_FREQUENCY_HZ` is used for documentation/logging only with the
> E32 driver.  The actual transmission frequency is determined by the E32
> module's hardware configuration.  Use the EBYTE RF Setting tool or AT
> commands to set the module's channel if you need a frequency other than the
> factory default.

## Docker setup

Replace the SPI device entries in `docker-compose.yml` with your UART port:

```yaml
devices:
  # Remove or comment out the spidev lines, then add your UART port:
  - /dev/ttyS0:/dev/ttyS0
  - /dev/gpiomem:/dev/gpiomem
```

## How the E32 driver works

### Transmitting a command

1. The `rfService` builds a JSON payload containing the RF code and E32
   connection parameters.
2. `rf_transmit_e32.py` is invoked via `child_process.execFile`.
3. The script opens the serial port, drives M0/M1 LOW (normal mode), and
   writes the code bytes to UART.
4. The E32 transmits the bytes as a LoRa packet on the configured channel.
5. A receiving E32 (at the blind motor) forwards the bytes to its own UART
   output, where a microcontroller (or another Pi) acts on them.

### Learning / capturing a code

1. `rf_receive_e32.py` is invoked with a timeout.
2. The script listens for an incoming LoRa packet on the serial port.
3. Received bytes are converted to a binary string and printed to stdout.
4. The Node service saves the code to `config/blinds.json`.

## Troubleshooting

### `Could not import e32 module` / `No module named 'serial'`

```bash
pip install pyserial RPi.GPIO
```

### `Permission denied on /dev/ttyS0`

Add your user to the `dialout` group:

```bash
sudo usermod -a -G dialout $USER
# Log out and back in, then verify:
id $USER
```

### No data received / module not responding

- Confirm M0 and M1 are wired correctly and driven LOW when in normal mode.
- Check that the UART port matches your Pi model (try `dmesg | grep tty`).
- Ensure the E32 baud rate matches `E32_UART_BAUD` (factory default is 9600).
- If AUX is not wired, increase the transmit guard time by reducing
  `RF_REPEAT_COUNT` and checking for interference.

### Both E32 modules must use the same channel and air data rate

Use the [EBYTE RF Setting](https://www.ebyte.com/en/pdf-down.aspx?id=1085) tool
(Windows) or AT commands to ensure both modules are on the same channel and
air data rate.  Factory defaults: channel 0x06 (416 MHz for 433-series → check
your module's datasheet for the exact mapping), air rate 2.4 kbps.
